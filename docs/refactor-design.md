# OpenPanda 重构设计

日期：2026-09-08；状态：设计提案，未实施。目标：成为有个人辨识度、适合长文阅读、可持续扩展的嵌入式与硬件技术博客。

## 1. 设计原则与范围

“高级感”落实为排版、留白、信息层次、一致的交互与可靠的状态，而不是堆砌动画。架构质量落实为可测试的业务边界、稳定契约和低风险发布，而不是框架数量。

保留文章、分类、标签关联、Markdown 编辑与图片上传、搜索、双语 UI、双主题、登录、可见性管理、AI 助手和工具库。已有中英 UI 不等于每篇文章有翻译；没有译文不生成虚假的语言链接。

本轮不建设微服务、Kubernetes、GraphQL、事件总线、用户社区或 Elasticsearch，不删除数据库或上传文件，不接管未跟踪的第三方项目。功能缺陷先修复，视觉与架构逐步迁移，不做一次性重写。

## 2. 技术决策

| 方案 | 优点 | 成本/局限 | 决策 |
| --- | --- | --- | --- |
| Vue/Vite + Go 模块化单体 | 最大化复用；先改善设计和可维护性 | SPA 本身不提供完整服务端正文 | 阶段一至三采用 |
| Nuxt + 现有 Go API | 复用 Vue，支持服务端渲染与页面元信息 | 新增 Node 运行时；认证、状态和部署均需适配 | 阶段四首选候选，PoC 达标后单独记录 ADR |
| Astro + 现有 Go API | 内容站低客户端 JS 潜力 | 动态编辑、权限预览与多交互业务要额外整合 | 备选，偏静态站方向时再评估 |
| Next.js + Node API | React 生态及全 TS 的可能性 | 重写 Vue 和 Go，迁移面大；不能保证更美观 | 当前不选 |
| 仅改 CSS、不改边界 | 快速见效 | 无法解决测试、发布和扩展问题 | 不作为完整方案 |

不宣称候选为最新版本。本轮不安装候选框架或测试库；实施前核查官方支持周期、现有 Node/TS 兼容矩阵、许可证、部署资源与依赖安全，并锁版本。先用已有 Vue、CSS、Go 标准测试工具落地；新增清洗、浏览器测试或 SSR 依赖必须有独立选型记录。

## 3. 视觉设计：安静的技术手记

### 页面信息结构

首页：紧凑导航 → 作者/站点介绍（唯一 h1）→ 编辑精选 → 最新文章 → 专栏索引 → 关于与页脚。精选需真实置顶能力；字段未交付时只显示最新内容，不伪造推荐数据。

文章页：返回文章链接 → 分类/标题/摘要/日期/阅读时长 → 正文与桌面目录 → 相关文章或返回入口。阅读时长按内容估算并注明；目录锚点稳定且避开粘性头部。代码块显示语言和复制结果，长代码/表格仅局部横向滚动，图片有尺寸及 alt；工程图不强制裁切。

列表与专栏：清晰标题、搜索/筛选、结果数量、文章流、可链接分页；筛选状态进入 URL，返回后保留。工具库保留现有路径，工具按需加载，不进入博客首页包。

后台：独立 AdminLayout，保留 Element Plus 表单/表格/编辑器，前台不共享后台视觉。统一草稿、已发布公开、已发布隐藏状态；删除与离开未保存编辑页需要确认。AI 不挤占公开导航。

移动端：320px 起不出现整页横向滚动；导航折叠；目录可展开；主要点击目标至少 44×44px。链接用原生链接语义，操作用按钮，支持键盘、新标签页和清晰焦点。

所有数据区域明确区分 loading、empty、error、success；错误有重试，不能以空列表掩盖请求失败。深浅主题、中英 UI、长标题、无封面、无分类均为必验状态。

## 4. 架构：按业务模块组织的单体

保持单仓库，不立即改包管理器、不为单个前端引入 monorepo 编排工具。Frontend/Backend 现有名称暂不变，避免 Docker/CI 路径一起失效。

### 前端边界

目标目录均在 `/home/hy/work/other/openpanda/Frontend/src/` 下：

- `app/`：启动、路由聚合、全局 provider。
- `layouts/`：PublicLayout、AdminLayout。
- `modules/content/`：文章/分类相关 pages、components、composables、api、types；内部再按增长拆分。
- `modules/auth/`、`modules/media/`、`modules/ai/`、`modules/tools/`：各自业务入口。
- `shared/ui/`、`shared/styles/`、`shared/http/`、`shared/lib/`：无业务归属的基础能力。

依赖方向为 app → modules → shared；shared 不导入 modules，模块不越过对方公共入口导入内部实现。页面只负责组合和路由状态，远端请求及状态转换放 composable/use case；Pinia 仅承载确需跨页面的客户端状态，不缓存所有服务端数据。API DTO 不直接成为展示组件 props 的唯一模型，适配逻辑集中，消除 any 和重复日期/URL 解析。

先移文章这一条纵向链路，旧路由转接新页面，其他模块后续迁移。目录移动不是验收终点，新增模块不需要修改无关模块实现才是目的。

### 后端边界

目标目录位于 `/home/hy/work/other/openpanda/Backend/internal/`：

- `content/`、`identity/`、`media/`、`ai/`、`settings/` 为模块。
- 每个复杂模块按 `domain`（规则）、`application`（用例及窄接口）、`transport`（Gin/DTO）、`repository`（GORM 实现）组织；简单模块不强制四层空目录。
- `platform/` 提供配置、数据库连接、日志、时钟等；`bootstrap/` 统一组装依赖。

transport → application → domain；repository 实现 application 定义的接口，由 bootstrap 注入。领域规则不依赖 Gin/GORM；禁止 controller 直接查数据库和暴露公共 DB 字段。不要建万能 BaseRepository；只抽取测试、替换和规则隔离真正需要的接口。

文章与标签更新用事务；列表 DTO 不返回全文；详情读取与阅读计数分离，计数失败不影响正文，后台任务必须有并发上限、取消和退出处理，不能无限创建 goroutine。分类删除有引用时返回明确冲突，不静默破坏文章关联。

## 5. 契约、权限与数据

- 首先冻结并核对 `/api/v1` 现有响应格式、分页和错误码；建立机器可验证契约的格式选型，不直接引入生成器。新旧客户端兼容期不直接改字段名。
- 保留 `/articles/:id`、`/articles/:id-slug`、分类与工具路径；canonical 统一到 ID+slug；slug 改动或旧 ID 链接在 SSR 阶段使用服务端 301/308，无循环，ID 仍是定位依据。
- 匿名读者仅能读取 is_published && is_public；列表、详情、搜索、热门、sitemap、未来 RSS 必须同一策略。隐藏和草稿均不可进入公共缓存。
- 管理员凭有效服务端验证身份访问管理读取；前端 token 存在不等于授权。建立匿名/过期/伪造/有效凭证与三种文章状态的矩阵测试。
- Markdown 原文保留；渲染结果只允许安全标签/属性/URL 协议，覆盖 script、事件属性、javascript URL、SVG 等攻击样例。清洗与服务端渲染一致；CSP 是补充，不是替代。
- 当前 JWT 行为先兼容。若 SSR 引入同源 HttpOnly/Secure/SameSite 会话 cookie，必须同时设计 CSRF/Origin 校验、退出失效与有效期；不能仅把 token 换位置。敏感响应 no-store，日志脱敏，AI 配置与凭据不进入公开响应。
- 上传验证文件签名、大小、扩展名和安全路径，保留旧 `/uploads` URL；静态资源不当作可执行内容。外部 AI 请求限制超时并响应客户端取消。
- 迁移先建立现有 schema 基线，再新增版本化迁移。采用 expand → 回填/校验 → 切流 → contract，旧字段至少保留一个兼容发布周期。不双写两套主数据库。

## 6. 渲染与缓存演进

阶段四 Nuxt PoC 仅验证首页和文章详情；仍由 Go 唯一承担业务规则和写入，Node 如引入仅承担页面渲染及必要同源适配，不再另建一套 Node CRUD 后端。

公开内容目标为可直接读取正文的服务端 HTML；后台编辑器保持客户端渲染。每个 SSR 请求独立状态，禁止共享用户状态和无保护 localStorage。主题/语言首屏与水合一致。

首次切流禁用共享 HTML 缓存，先满足隐私正确性；缓存只有在权限隔离、发布/隐藏/删除即时失效测试通过后启用。隐藏内容若无法可靠清除旧缓存，应先停用对应缓存再开放隐藏功能，不接受 TTL 内泄漏。Redis 当前不是必需业务依赖，不为“先进”强行接入。

公开页具备独立 title、description、canonical、OG、文章结构化数据和正确 HTTP 404；只为真实翻译提供 hreflang。sitemap/RSS 只包含公开已发布内容。框架迁移失败时保留阶段三视觉与模块成果，但不能把 SSR/SEO 目标标为完成。

## 7. 发布与风险控制

保留 PostgreSQL、上传挂载与 Docker Compose；未来 Node SSR 增加独立服务而不重建数据库。CI 按检查 → 测试 → 构建 → 预发布 → 冒烟 → 固定 SHA 发布执行，失败停止部署。

上线前备份数据库与上传文件到隔离位置并执行恢复演练，校验记录、关联、文件校验和与可见性。正常回滚优先回退应用和路由，不把恢复旧库当成默认回滚，以免丢失新写入。破坏性变更必须单独维护窗口及数据恢复方案。

采用请求 ID、结构化脱敏日志、API 延迟/错误率、数据库 readiness 与进程 liveness；AI 故障不阻断文章阅读。个人站先保持少量部署单元，流量和容量实测前不承诺扩容收益。
